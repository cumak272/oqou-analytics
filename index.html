KPI dashboard and data pipeline for a mobile app

I built a reporting system for my language-learning app oqou. Every morning it pulls data from four sources, cleans it, loads it into a SQL database and updates a dashboard. I use it to track growth, find where users drop off and decide what to work on next.

The problem

The app's data was spread across four tools, and they did not agree with each other.

Scattered sources

Downloads were in App Store Connect, usage in Google Analytics 4, subscriptions in RevenueCat and website search in Google Search Console. Comparing anything meant opening four tabs.

Numbers that disagreed

Each source counts a "new user" differently, uses different time zones and finalises data with a different delay. My own test installs were also counted as real users.

Questions without answers

Do people who start a trial come back? Which onboarding step loses the most users? Do social media posts bring downloads? No single tool could answer these.

What I built

A daily ETL job feeds a SQL data model. One metric catalog defines every KPI, and the dashboard and the morning report both read from it.

Data quality: one number from three sources

Downloads are counted by App Store Connect, RevenueCat and Google Analytics, and they never match exactly. The pipeline compares them every day and picks the most reliable figure for each day.

Downloads per day by source

App Store Connect is the final number but arrives two days late, so its last two days are empty here, not zero.

Checks built into the pipeline

  • Source priority per day: App Store Connect when it has the day, otherwise RevenueCat minus test installs, otherwise GA4. Each figure is labelled Final, Provisional or Live.
  • Test installs removed: my own simulator and screenshot runs are detected by pattern and excluded from every figure.
  • Missing is not zero: when a source fails, the value is stored as "not measured". A run where no source answered stops with an error instead of reporting a quiet day.
  • Unsettled days are re-loaded: GA4 can still revise a day for 48 hours, so the job loads those days again until they settle.
  • Small samples flagged: a rate with fewer than 10 users in the denominator is marked and never highlighted.

Metric definitions and SQL

Each KPI is defined once in a catalog, so the dashboard, the report and any ad-hoc query calculate it the same way.

Example: Day-1 retention

Definition
Share of users who were active again one day after their first session
Numerator
Cohort members active on day 1
Denominator
Users whose first session was on the cohort date
Grain
Daily cohort; weekly and monthly values are recomputed from summed numerator and denominator, never averaged
Caveats
A cohort younger than one day has no value yet. Denominator under 10 is flagged as a small sample.
Source
GA4 cohort report, table fct_retention

Example query: a rate by country

Ratios are summed first and divided once, so a big country is not weighted the same as a small one.

SELECT x.key                    AS country,
       SUM(x.value)             AS trials,
       SUM(y.value)             AS new_users,
       ROUND(100.0 * SUM(x.value)
             / SUM(y.value), 1) AS trial_rate
FROM   fct_daily_dim x
JOIN   fct_daily_dim y
  ON   y.date = x.date
 AND   y.dimension = x.dimension
 AND   y.key = x.key
 AND   y.metric = 'new_users'
WHERE  x.dimension = 'country'
  AND  x.metric = 'trial_users'
  AND  x.date BETWEEN :from AND :to
GROUP BY x.key
HAVING SUM(y.value) >= 10
ORDER BY trial_rate DESC;

What the data changed

Two findings that changed what I worked on.

Retention, not the paywall, limited sales

My first idea was to redesign the paywall because few trials turned into paid subscriptions. The data said otherwise. The first session worked well, but most new users never came back after day 1, and users who returned on a second day started trials several times more often than one-day users. A paywall change moves how many trials start; retention moves how many people buy. So the next release focuses on bringing readers back on day 2, and the retention cohorts above measure whether it works.

The old report said zero when it wasn't

When I compared the pipeline's revenue figures with the payment provider's own charts, they did not match. The old report read a field that the API does not return, so it showed no paid subscriptions while payments had come in. Since then every money figure is reconciled against the source's own charts, and a field that is missing is reported as "not measured", not as zero.
